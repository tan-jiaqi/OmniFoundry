<a id="common"></a>

## 1. 共同点：架构已经收敛

四者的流水线骨架几乎相同，没有例外：

| 环节 | 四者一致的做法 |
| --- | --- |
| 感知 | **全部用大模型写描述，没有一个用专用感知工具**。没有声音事件检测、没有检测跟踪、没有人工标注。JointAVBench 用了外部 ASR 字幕，但那是现成数据，不是它自己跑的 |
| 媒体处理 | 只用 ffmpeg 切片抽帧 |
| 切分 | 先把视频切成片段或事件，再逐段描述 |
| 出题 | **答案都由大模型生成**，不是程序从结构化标注算出来的 |
| 题型 | 都维护一份题型目录（13 到 15 类），按题型给不同指令 |
| 作答形式 | 以多选题为主 |
| 筛查 | 都有"只给题目不给视频"的盲测 |

这一点对本项目有直接意义：早期版本（`archive/OmniFoundry-next`）走的是"专用工具感知 → 程序算答案"，四个项目里没有一个采用这条路线，该版本的实际产量也接近零。

<a id="modality"></a>

## 2. 关键区别：如何证明一道题必须同时用到音和画

这是差距最大的一项，也是各家产量数字不可直接比较的根源。

| 项目 | 判定方式 | 强度 |
| --- | --- | --- |
| TraceAV-Bench | 生成模型自己给每一跳贴 `audio` / `visual` 标签，代码只检查标签集合里两种都有（`src/step3_agentic_question_generation/agentic_question_generation_prompts.py:83-90`） | **最弱**。标签从不校验；数据样例中存在证据是台词、标签却写 `visual` 的情况 |
| JointAVBench | 纯文本判断"题目、答案、解释是否*提到*了两个模态"（`generation_pipeline/general_check.py:141-146`） | **弱**。问的是"是否提及"，不是"能否只靠一个模态答出" |
| OmniReasoning | 给模型**随机挑的 1 个事件片段**的描述去答，答对少于 2/3 即通过；补集测试因 `segment_id` 从未生成而恒等于全量描述；两项**任一通过**即算通过（`verification/modality_gate.py:425-460`） | **中等偏弱**。单个随机片段几乎不含答案，因此基本总是通过 |
| **本项目** | 给**全部**音频描述或**全部**画面描述去答；再用**真实的静音视频和纯音频**各采样 3 次；阈值用 31 条人工标注校准 | **最强** |

**后果**：JointAVBench 的 2853 道"联合题"与本项目的 `av_strict` 不是同一量纲。本项目 66 道题若按其标准判定，几乎全部会算作联合题。横向比较产量时必须先对齐口径。

**阈值校准记录**（本项目，基于 31 条人工标注）：

| 判定阈值 | 判为联合 | 与人工一致 | 漏判 |
| --- | --- | --- | --- |
| 单模态答对 ≥2/3 即算捷径 | 4 | 4 | 11 |
| 单模态答对 3/3 才算捷径 | 14 | 12 | 3 |

采用后者。人工判定需要双模态的有 15 道，自动判定 14 道，精确率 12/14。

<a id="detail"></a>

## 3. 逐项对照

### 3.1 描述阶段

| | 通道数 | 屏幕文字 | 音画分离 |
| --- | --- | --- | --- |
| OmniReasoning | 2（音频 / 画面）+ `audio_type` | **内联在画面描述中**（prompt 要求逐字转录） | 分离 |
| JointAVBench | **5**（画面、音乐、音效、语音情绪、字幕），三个模型分别跑 | **明令禁止写入画面描述**（`gen_caption/video_caption.py:35`） | 分离，且禁止音频描述写台词、禁止从台词内容推断情绪 |
| TraceAV-Bench | 1（音画融合为一段） | — | **不分离**；纯音频文本从不保存，结构上无法做模态消融 |
| 本项目 | 2 + `audio_type`（同 OmniReasoning） | **内联**（同 OmniReasoning） | 分离 |

**JointAVBench 在此项领先**：它在描述阶段就堵住捷径，而 OmniReasoning 和本项目是先制造泄漏、再事后过滤。本项目 `visual_sufficient` 占比偏高，这是根因之一。

### 3.2 出题构造

| | 方式 | 扇出粒度 |
| --- | --- | --- |
| OmniReasoning | 给题型定义 + 全部描述，模型自由发挥 | `--questions-per-video` 默认 1；多道题是对同一份描述出不同变体（`stage2_generate.py:1393-1405`） |
| JointAVBench | **每题型一个固定骨架**，写死哪个模态给指称、哪个给答案，带唯一性前提和 `[Unavailable]` 中止（`generation_pipeline/prompts.py:3,7,9`） | **每片段 × 每题型**（`generate_qa.py:93-151`），候选池最大 |
| TraceAV-Bench | 两段式：先出"出题方向"（focus / answer_hint / distractor_hint），再写题 | 每视频每题型 1 道，共 15 题型 |
| 本项目 | **锚点驱动**：程序先枚举音画证据组合，再让模型围绕指定锚点出题；叠加桥接字段与 `[Unavailable]` | 每锚点 × 题型，每视频 5 道 |

**锚点挖掘是本项目独有的**（`omnifoundry/policies/anchor_miner.py`）：其余三家都没有"先用程序找出可用的跨模态证据对，再让模型填空"这一步。JointAVBench 最接近，但它按片段扇出，片段内选什么证据仍由模型决定。

实测效果（50 个视频）：引入锚点后每视频产量 0.63 → 1.32 道，每次尝试产出率 16.8% → 23.0%，盲测存活率 34.7% → 46.0%。模型不必自行寻找切入点，写出的题更扎实。

### 3.3 正确性核验

| | 对照描述 | 对照真实媒体 |
| --- | --- | --- |
| OmniReasoning | 描述条件求解器 | 线索对照切片核验，但**音频线索被跳过**（默认用纯视觉模型）；refine 阶段把音频步骤当作真值 |
| JointAVBench | 文本质量判断 + 按题型的描述子集歧义检查 | **完全没有** |
| TraceAV-Bench | 盲测 + LLM 评审，且评审**默认只是建议、不丢弃**（需显式传 `--drop-failed-verification`） | 无 |
| 本项目 | 描述条件求解器（严格：解析失败即拒，答案不一致即拒，不静默改答案） | **音频和视觉线索都对照真实片段核验**；完整视频下必须答对 |

### 3.4 产出物

| | 评测集 | 训练数据 | 推理过程 | 质量分档 |
| --- | --- | --- | --- | --- |
| OmniReasoning | 1150 题 | **SFT 112K + RL 19K** | 有（第 4 阶段合成） | 无 |
| JointAVBench | 2853 题，15 题型 | 无 | 无 | 无 |
| TraceAV-Bench | 2200 题，578 视频 | 无 | 无 | 无 |
| 本项目 | — | SFT + RL（同 OmniReasoning 格式） | 有，且分普通式与**佐证式**两种 | **high / medium / low + 模态标签** |

**质量分档是本项目独有的**。另外三家都是二元判定，不通过即丢弃。本项目区分硬失败（答案不可靠，丢弃）与软失败（答案正确但题目偏易，降级保留并如实标注），详见 `omnifoundry/quality.py`。实测该设计使产量从 12 道升至 31 道，是单项提升最大的改动。

对 `medium` / `low` 档的题，推理过程改用佐证式写法：先从主模态得出答案，再说明另一模态如何印证，不假装两个模态缺一不可。

### 3.5 工程

| | 缓存与续跑 | 可复现性 |
| --- | --- | --- |
| OmniReasoning | 按产物缓存；**续跑键用输入文件行号**，输入一变即错位 | 中等 |
| JointAVBench | 分阶段脚本 + JSON 文件 | 一般；`coverage.json` 的生成代码缺失 |
| TraceAV-Bench | — | **差**：第 2 步写 `active_entities`、第 3 步读 `processed_entities`，字段对不上；分段结果不含 `event_id` 而下游必须要，照代码跑出来是零条轨迹 |
| 本项目 | **内容哈希的两层缓存**（模型调用 + 阶段产物）；改一个 prompt 只重算下游 | 每条记录带 lineage；`funnel` / `compare` 可量化对比任意两轮 |

**TraceAV-Bench 的 README 与代码不符之处**（已逐项核对）：去重、半自动人工标注、`difficulty` 字段、按模态标注实体的机制，在代码中均不存在或从未被写入。

<a id="behind"></a>

## 4. 本项目落后的地方

1. **规模**：他们 2000 到 3000 道题，本项目目前 66 道。这是最大差距。
2. **描述卫生**：JointAVBench 的 5 通道分离更干净，是本项目 `visual_sufficient` 偏多的根因。
3. **长视频**：TraceAV-Bench 处理平均约 35 分钟的视频，本项目目前只做 1 到 2 分钟。
4. **桥接模板成熟度**：JointAVBench 每个题型的骨架经过打磨，本项目只是简化版。
5. **"超越视频"路线**：OmniReasoning 的 RBY（看完视频把知识迁移到新场景 + 生成配图）完全未实现，而那是它 400 道评测题和相当部分训练数据的来源。
6. **训练闭环**：OmniReasoning 有 MFSD 训练方法，用线索做 token 级信用分配。本项目只产数据，尚未验证数据能否提升模型。

<a id="conclusion"></a>

## 5. 结论

本项目本质上是 **OmniQA 的骨架 + JointAVBench 的构造思路 + 自有的严格判定与质量分档**。

已验证有效的三项改动，按提升幅度排序：

| 改动 | 效果 |
| --- | --- |
| 软失败降级保留而非丢弃 | 12 → 31 道 |
| 按锚点扇出 | 31 → 66 道，`av_strict` 4 → 21 道 |
| 门控阈值按人工标注校准 | `av_strict` 4 → 14 道（同一批数据重新判定） |

已验证**无效**的假设，不要重复尝试：

- 整段视频的音画词汇重复度无法预测题目联合性（高重复组反而联合率更高），不能作为选片规则。
- 限制单一题型在视频内的占比：题型多样性有改善（排序题占比 88% → 72%），但总产量下降（66 → 54 道），`av_strict` 也下降（21 → 16 道）。
- 出题 prompt 要求"干扰项取自视频别处的真实细节"：导致答案歧义，求解器一致率从 100% 跌至 80%。

下一步的三条路，按推荐排序：

1. **采纳 JointAVBench 的描述卫生**：画面描述不再内联屏幕文字，音频按台词 / 音效 / 音乐 / 说话人特征分通道。直接针对两个最大损失点（`visual_sufficient` 偏多、线索核验 50% 失败）。代价是全部描述需用 Pro 模型重跑。
2. **放量**：架构已验证，两批共 43 道人工抽检全部正确，剩下的是算力与时间。需先解决网关稳定性（曾出现持续 3.5 小时、25% 调用失败的故障）。
3. **补"超越视频"路线**：属于新功能，应排在前两项之后。
